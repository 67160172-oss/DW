# Retail ETL Pipeline

โปรเจกต์นี้เป็น ETL Pipeline สำหรับข้อมูลค้าปลีก โดยโหลดข้อมูลคำสั่งซื้อเข้าสู่ Data Warehouse
แบบ Star Schema พร้อมกลไกตรวจสอบคุณภาพข้อมูล (Data Quality) และรองรับการรันซ้ำ (Idempotent)

## 1. การติดตั้ง

ติดตั้งไลบรารีที่จำเป็น:

```bash
pip install pandas
```

จัดวางไฟล์ตามโครงสร้างนี้ก่อนรัน:

```
lab/
├── pipeline.py
├── data/
│   ├── customers.csv
│   ├── products.csv
│   ├── orders_batch_1.csv
│   ├── orders_batch_2.csv
│   └── orders_batch_3.csv
└── output/            (ถูกสร้างขึ้นเองตอนรันสคริปต์)
```

## 2. การใช้งาน

สั่งรันด้วยคำสั่งเดียว:

```bash
python pipeline.py
```

เมื่อรันแล้ว สคริปต์จะประมวลผลข้อมูลทีละรอบ รวม 4 รอบ เพื่อแสดงให้เห็นทั้งพฤติกรรม
Idempotency และการโหลดข้อมูลแบบ Incremental:

1. โหลด `orders_batch_1` เป็นครั้งแรก
2. โหลด `orders_batch_1` ซ้ำอีกครั้ง — ใช้ตรวจว่าจำนวน fact rows ไม่เพิ่มขึ้น
3. โหลด `orders_batch_2` — รับเฉพาะข้อมูลที่ยังไม่เคยมี
4. โหลด `orders_batch_3` — รับเฉพาะข้อมูลที่ยังไม่เคยมี

ไฟล์ผลลัพธ์ทั้งหมดจะอยู่ในโฟลเดอร์ `output/`:
- `retail_dw.db` — ฐานข้อมูล SQLite ที่จัดเก็บในรูปแบบ Star Schema
- `quarantine.csv` — แถวข้อมูลที่ไม่ผ่านเกณฑ์คุณภาพ พร้อมระบุ `reason_code`
- `pipeline_run_log.csv` — บันทึกผลการรันของแต่ละรอบ

## 3. รูปแบบ Star Schema

| ตาราง | ระดับความละเอียด (Grain) |
| --- | --- |
| `dim_customer` | หนึ่งแถวต่อลูกค้าหนึ่งราย (`customer_id`) |
| `dim_product` | หนึ่งแถวต่อสินค้าหนึ่งรายการ (`product_id`) |
| `dim_date` | หนึ่งแถวต่อหนึ่งวัน (สร้างจาก `order_datetime`) |
| `fact_sales` | **หนึ่งแถวต่อ `order_id` หนึ่งรายการที่ผ่านการตรวจสอบแล้วเท่านั้น** |
| `quarantine` | รายการที่ตกเกณฑ์คุณภาพหรือถูกแทนที่ด้วยเวอร์ชันที่ใหม่กว่า พร้อม `reason_code` |
| `pipeline_run_log` | ประวัติ/watermark ของการรันแต่ละ batch |

ข้อจำกัดด้านความไม่ซ้ำ (Uniqueness):
- คอลัมน์ `dim_customer.customer_id`, `dim_product.product_id`, `dim_date.date_key`,
  `dim_date.full_date` และ `fact_sales.order_id` ทั้งหมดกำหนดเป็น `UNIQUE` เพื่อกันข้อมูลซ้ำ
  ตั้งแต่ระดับฐานข้อมูล
- ตาราง `fact_sales` ใช้คำสั่ง `INSERT ... ON CONFLICT(order_id) DO UPDATE ...`
  ร่วมกับเงื่อนไข `WHERE excluded.updated_at > fact_sales.updated_at` ทำให้การรันซ้ำ
  **ไม่ทำให้จำนวนแถวเพิ่มขึ้น** และอัปเดตเฉพาะกรณีที่ข้อมูลใหม่กว่าเดิมเท่านั้น

## 4. ผลการรันทั้ง 4 รอบ

| รอบ | rows_read | rows_valid | rows_loaded | rows_rejected | สถานะ |
| --- | --- | --- | --- | --- | --- |
| batch_1 (ครั้งแรก) | 420 | 389 | 389 | 31 | success |
| batch_1 (รันซ้ำ) | 420 | 389 | **0** | 31 | success |
| batch_2 | 424 | 386 | 386 | 38 | success |
| batch_3 | 424 | 386 | 385 | 38 | success |

**หมายเหตุสูตรการนับ**: `rows_read = rows_valid + rows_rejected` โดยนับ**ก่อน**ขั้นตอน
deduplicate/incremental filter — `rows_valid` หมายถึงแถวที่ผ่านการตรวจสอบทั้งชนิดข้อมูล
ช่วงค่าที่ยอมรับได้ และความสัมพันธ์เชิงอ้างอิง (referential integrity) ส่วน `rows_loaded`
คือจำนวนแถวที่ upsert เข้า `fact_sales` จริง หลังหักรายการซ้ำหรือรายการที่เคยโหลดไปแล้วออก

สรุปผลรวมหลังโหลดครบทั้ง 3 batch:
- จำนวนแถวใน fact table: **1,159 แถว** (ไม่มี `order_id` ซ้ำเลย)
- ยอดขายสุทธิรวม (net_amount): **2,841,792.10**
- จำนวนรายการที่ถูกกักไว้ใน quarantine ทั้งหมด: **138 แถว**

สาเหตุที่พบใน quarantine เรียงจากมากไปน้อย:
`customer_id_not_found` (30) · `invalid_order_datetime` (28) · `quantity_out_of_range` (19) ·
`discount_pct_out_of_range` (16) · `product_id_not_found` (15) · `invalid_quantity_type` (14) ·
`invalid_unit_price_type` (12) · `duplicate_order_id_superseded` (4)

## 5. มุมมองเพิ่มเติม — ทำไม Production Pipeline จึงมักให้น้ำหนักกับ Availability มากกว่า Strictness

ข้อมูลจากระบบต้นทางในโลกจริงแทบไม่เคยสมบูรณ์แบบ 100% ถ้า Pipeline ถูกออกแบบให้หยุดทำงาน
ทั้งระบบทันทีที่เจอแถวข้อมูลผิดปกติเพียงแถวเดียว (แนวทาง fail-fast) ผลที่ตามมาคือฝั่งวิเคราะห์
และรายงานจะไม่ได้รับข้อมูลใหม่เลย ทั้งที่ข้อมูลส่วนใหญ่ในแต่ละ batch อาจถูกต้องอยู่แล้วถึง 99%
ความเสียหายจากการที่ "ไม่มีข้อมูลเลย" มักร้ายแรงกว่าการที่ "มีข้อมูลบางส่วนยังไม่สมบูรณ์" เพราะ
ธุรกิจยังพอตัดสินใจต่อไปได้จากข้อมูลส่วนใหญ่ที่ถูกต้อง ในขณะที่ระบบล่มจะกระทบผู้ใช้งานปลายทาง
ทุกกลุ่มพร้อมกันทันที

แนวทาง Quarantine ร่วมกับ `reason_code` ที่ใช้ในโปรเจกต์นี้ เปรียบเสมือนการ "คัดแยกเคสที่มีปัญหา
ออกจากเคสปกติ" กล่าวคือปล่อยให้ข้อมูลที่ผ่านมาตรฐานไหลต่อไปได้ตามปกติเพื่อรักษา Availability
ในขณะที่ข้อมูลที่มีปัญหาจะถูกเก็บแยกไว้เพื่อตรวจสอบและแก้ไขในภายหลัง โดยไม่ทำให้ระบบทั้งหมดหยุดชะงัก
วิธีนี้ยังช่วยให้ตรวจสอบย้อนหลังได้สะดวก (auditability) เนื่องจากทุกแถวที่ถูกปฏิเสธมีเหตุผลกำกับไว้ชัดเจน

ทั้งนี้ การให้ความสำคัญกับ Availability ไม่ได้หมายความว่าจะละเลยคุณภาพข้อมูล — กฎที่ส่งผลต่อ
ความถูกต้องของตัวเลขทางการเงินโดยตรง (เช่น `unit_price` ติดลบ หรือ Foreign Key ที่อ้างอิงไม่ถึง)
ยังคงต้องถูกคัดกรองอย่างเข้มงวด เพียงแต่การคัดกรองนั้นเกิดขึ้น "ที่ระดับแถวข้อมูล" ไม่ใช่ "ที่ระดับ
ทั้ง batch" กล่าวโดยสรุปคือ Strictness ควรถูกบังคับใช้ในระดับ record ไม่ใช่ระดับ pipeline
เพื่อให้ภาพรวมของระบบยังคง Available และน่าเชื่อถือได้ในระยะยาว
